# Testing

## Requirements

- Node.js 24 or newer (`engines` in `package.json`).
- npm, to install the single development dependency (`typescript`, used by
  the test suite to parse the runner source).
- Git 2.45 or newer on `PATH` (see [cli.md](cli.md#git-version)). Tests
  create temporary Git repositories in the system temporary directory.
- Corepack on `PATH`, with pnpm 11.20.0 already in the local Corepack cache.
  Some tests run the real pnpm offline from that cache. To populate it once:

  ```sh
  corepack install -g --cache-only pnpm@11.20.0
  ```

- npm on `PATH` (it comes with Node.js): the package tests run `npm pack`
  and `npm install --offline`.
- A POSIX environment: tests use `which` to locate programs.

The tests do not need the Git history of this repository: a shallow clone or
a copy of the working tree with a single commit is enough. The tests do not
start the Codex or Claude CLIs; agent rounds and processes are replaced with
test doubles.

## Test names, messages and comments

Test and subtest names, assertion messages and comments are in English. A
test name describes the behavior it checks (for example
`task schema: English aliases give the same parse result as Polish headings`),
not the work item, stage, review finding or commit that introduced it: no
stage identifiers, finding codes or commit hashes. Comments describe the
behavior and the reason for a check, not the history of how it was written.
A `[golden]` test name starts with the area it compares, followed by
`[golden]:` and what must match the snapshot; the name is stored in the
`test` field of the snapshot, so renaming such a test means regenerating the
snapshot (only that field changes).

Polish text stays where it is test data: task files with Polish headings,
expected messages of the `pl` locale, Polish markers in agent output and the
`pl` prompts.

Two known exceptions remain. Subtests named from data tables (labels such as
`'domyślny'` or `'profil CLI'`) keep their Polish labels: some of these
labels are also keys of snapshot entries, so they are test data. The `test`
field of `scripts/fixtures/golden/cli-profile-history.json` is still Polish;
that snapshot is not regenerated by `update-golden.mjs` and its `test` field
does not follow any test name.

## Golden snapshots

The compatibility tests marked `[golden]` compare the output of the current
runner with snapshots in `scripts/fixtures/golden/`: full runs of the
scenarios (report, events and, for the Polish locale, the terminal output),
the argv, environment and results of the built-in provider adapters, and the
CLI parser and usage. Each snapshot describes the output of an earlier
version of the runner (the `baseline` commit in the file); before the
snapshots replaced tests that read that code from Git, each one was checked
against the output of its baseline.

A snapshot entry has a readable header (status, stage, error code, number of
rounds, key report fields, argv) and SHA-256 digests of the canonical JSON
(sorted keys) of the large subtrees; where key order mattered before, an
`orderedSha256` of the unsorted JSON is kept as well. The scenarios run in a
fixed synthetic environment (`GOLDEN_ENVIRONMENT` in the test file), not in
the environment of the machine. Every Git call in these scenarios, including
the calls the runner makes with `process.env`, ignores the machine's Git
configuration: `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, no
inherited `GIT_*` variables, and a fixed author, committer and commit dates
(`withGoldenGitEnvironment`, which restores `process.env` afterwards). A test
checks that the snapshots still match with a hostile user Git configuration.
Snapshot files are named after what they cover (for example `runs-default`,
`adapters-codex-claude`, `cli-locale-pl`). The test file
lists every normalization in `GOLDEN_NORMALIZATIONS` (for example wall-clock
`durationMs` and paths of temporary directories); each snapshot records the
ones it uses.

When an entry differs, the test prints the changed header fields and names
the changed subtrees, and writes the full current value to a directory in
the system temporary directory. A missing snapshot fails the test.
`npm test` never writes snapshots.

A change in runner behavior is a change in a snapshot. Update snapshots on
purpose, by hand, and let the diff show up in review:

```sh
node scripts/fixtures/update-golden.mjs [snapshot-name ...]
git diff scripts/fixtures/golden/
npm test
```

The script runs the `[golden]` tests and copies the candidates of the
differing snapshots (or only of the named ones) into
`scripts/fixtures/golden/`. Explain in the pull request why the behavior
changed. The script exits with a non-zero code when a failing test left no
candidate or a requested snapshot was not updated. `cli-profile-history.json`
is a one-time record of a historical fact and is not generated by the script.

## Running

```sh
npm install
npm test
```

`npm test` runs `node --test scripts/agent-review-loop.test.mjs`, the test
file of the core. It imports `scripts/ringi-cli.test.mjs`, the tests of the
`ringi` command (`init`, `doctor`, `run`), which start `bin/ringi.mjs` on
synthetic repositories with stand-in agent CLIs that only answer
`--version`; its `run --dry-run` test uses the real pnpm offline from the
local Corepack cache. It also imports `scripts/ringi-package.test.mjs`, the
tests of the npm package (see [Package tests](#package-tests)).

The examples are checked separately and are not part of `npm test`:

```sh
node --test examples/validate-examples.test.mjs
```

## Package tests

`scripts/ringi-package.test.mjs` checks the npm package without network
access. npm runs with `--offline` and its own empty cache, user
configuration and home directory in the system temporary directory; pnpm
runs offline from the local Corepack cache. The package has no dependencies,
so installing the tarball fetches nothing.

- **Contents:** `npm pack --dry-run --json` lists exactly the files of the
  `files` field in `package.json`: `bin/`, `scripts/` without tests and
  without `scripts/fixtures/`, `examples/` without its test, `docs/`
  (including `docs/development/`, which the default profile's task classes
  point to), `LICENSE`, `NOTICE`, `README.md`, `CHANGELOG.md`,
  `SECURITY.md` and `package.json`. No `*.test.mjs`, snapshots, dotfiles,
  `.github/` or `node_modules`, and no packaged file contains an identifier
  of a work item. Every relative import of a packaged module is packaged,
  the only bare imports are `node:` built-ins, and the import graph of
  `bin/ringi.mjs` reaches the runner modules.
- **Installation:** `npm pack` into a temporary directory; with npm,
  `npm install --offline --save-dev <tarball>` in a plain project and
  `npm exec --offline -- ringi --version`; with pnpm, the tarball as a
  `file:` dev dependency of a synthetic Git repository (`package.json` with
  `packageManager`, `AGENTS.md`, `CLAUDE.md`, a working branch),
  `pnpm install --offline`, then through `node_modules/.bin/ringi`:
  `--version`, `init --dry-run`, `init`, a commit of the profile and task,
  `doctor --json` (`runner-location` is `warn` in both variants, because the
  runner lives in `node_modules` of the repository; without agent CLIs on
  `PATH` every other check is `ok` except `implementer-cli`, `fail`, and
  `reviewer-cli`, `warn` because it is not checked; with stand-in CLIs every
  other check is `ok`) and `run --dry-run` (`DRY_RUN_OK`, nothing changed in
  the repository). Finally a real run with a stand-in writer that changes
  `scripts/agent-review-loop-lib.mjs` in `node_modules` and then fails: the
  run stops with `RUNNER_MODIFIED` at stage `post-codex`, and the round's own
  failure is kept as an integrity violation.
- **Workflows:** a text check of `.github/workflows/` (not a YAML parser):
  actions pinned to a commit SHA, no `pull_request_target`, a read-only
  token by default, `id-token: write` only in the release job; no secrets
  and no `NODE_AUTH_TOKEN` in either workflow; the release job's npm
  version check, run
  against sample versions, fails below 11.5.1.

The workflows themselves are not run by the tests.

## What the core tests cover

`scripts/agent-review-loop.test.mjs` exercises the runner through its exported
functions and `internal` helpers, without real agents. This includes task
parsing (including the task schema and its aliases), profile validation
(including the pnpm and git argv allowlists, required gate rules and the task
schema), the prompt texts (compared byte for byte with a copy of the texts
before they moved to `scripts/agent-review-prompts.mjs`), the git and pnpm
guards, gate execution, snapshots,
secret detection, dependency and Corepack cache fingerprints, review policy and
fallback, finding identity across rounds, analysis mode, the report and the
dashboard. Part of the suite also checks that the runner's surface (CLI
options, codes and selected literals) has not changed unintentionally.

## Writing tests

- Keep tests deterministic and offline. Use synthetic repositories in the
  system temporary directory, as the existing helpers do.
- A behaviour change in the runner comes with a test that fails without it.
- Do not loosen a fail-closed check to make a test pass.
